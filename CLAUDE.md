@AGENTS.md

# urantiahub-v2

The new UrantiaHub: a reader for the Urantia Papers. Step 1 is the public reader.
Spec and plan: kept outside this public repo, in the private `urantia` workspace folder under `docs/superpowers/`.

## Commands

- `bun run dev` — development server
- `bun run test` — unit tests (Vitest)
- `bun run e2e` — browser tests (Playwright) against recorded API data
- `bun run typecheck`, `bun run lint`, `bun run build`
- `bun run sync:index` — rewrite `src/content/paper-index.json` from the live API

## Rules

- Next.js is pinned to 16.3.1. Read `node_modules/next/dist/docs/01-app/` before you use a Next.js API. `proxy.ts` replaces `middleware.ts`. Cache Components are on, so `dynamic`, `dynamicParams`, and `revalidate` route options do not exist.
- Only `src/content/index.ts` (the Papers) and `src/account/gateway.ts` (a reader's own data) import `@urantia/api`. Only `src/analytics/index.ts` imports `posthog-js`. Only `src/account/deps.ts` imports `@urantia/auth/server`.
- No test file under `src/app/`.
- Two root layouts: `src/app/(en)/layout.tsx` and `src/app/(es)/es/layout.tsx`, both through `RootShell` (`lang` on `<html>`). A move between the languages is a full page load. An address with no route gets `src/app/global-not-found.tsx` (the `globalNotFound` flag). In a route group Next.js adds a fixed suffix to a share image address (`opengraph-image-kvl95g`), so a test reads that address from the page.
- Spanish (`NEXT_PUBLIC_SPANISH`): the words of the Hub in each language are in `src/i18n/messages/` (a key missing in Spanish fails the type check), and the addresses in `src/i18n/paths.ts`. The Spanish titles are in `src/content/paper-index.es.json`, written by `bun scripts/sync-paper-index.ts --lang=es`.
- The language follows the reader (Kelson, 2026-10-24; spec `docs/superpowers/specs/2026-10-24-urantiahub-v2-spanish-everywhere-design.md` in the workspace): the last choice on any device wins. The browser keeps it in `hub:lang` with its time in `hub:lang-at` (`setReadingLang`); a signed-in reader's choice goes to `PUT /api/me/lang` at once, with `keepalive`, and the pull applies the newer one (`sync.ts`). The first page of a visit opens in that language when it has a twin: `LANG_MOVE_SCRIPT` (`src/reader/lang-move-script.ts`) runs first in `<body>` while Spanish is on, reads the `hrefLang` alternate link, and marks the tab with `hub:visit` in `sessionStorage`, so a later page of the visit never moves; the page that moves is hidden first. The script also marks the first page (`data-first-page`), and the pull moves that page to its twin (`moveToTwin`) when only the account knew the language. A page with no twin stays. A sign-out removes `hub:lang-at`: the device keeps its language, but with no time it never goes into the next reader's account. The sign-in start names the browser's choice (`signInHref`), and the callback returns to the twin in the newer of that choice and the account's (`twinPath`). The API gives `lang` in the notice list for Part 2.
- The Spanish pages of Part 2 (2026-10-24): `src/app/(es)/es/error.tsx` is the Spanish error page (`ErrorView`). A malformed escape under `/es/` rewrites to `/es/no-encontrado`, a static route that calls `notFound()`: the dynamic `[...rest]` route answered 500 there ("failed to decode param"). A Spanish 404 sends `<html id="__next_error__">` with no `lang` in the raw HTML, and the client sets `lang="es"`. The offline page of `public/sw.js` speaks the language of the address; its words are copies of `src/i18n/messages`, and `src/notices/sw-offline.test.ts` holds them equal. A Spanish page names no share image (`pageMetadata`): `src/app/(es)/es/opengraph-image.tsx` gives it, and `/es/documentos` has a copy of that file, because the image of `/es` does not reach a segment whose child has its own image. One manifest, with `start_url` `/`: the move script opens a Spanish reader's first page at `/es`.
- The notices speak the reader's language (`Due.lang`, from `hub.lang`; English with none). The words are `messages(lang).mail`. The daily notice of a Spanish reader quotes the Spanish paragraph; when it fails, that reader gets none that run and the claim goes back. A release reaches a Spanish reader only when its entry has `es` (a test holds `es` on each `notify` entry after 2026-10-24); the Spanish release mail is the plain frame, never the mail with pictures. The streak push stays English until Spanish section titles exist (Part 4), and the off page and the settings page keep their English addresses until they have twins. The English mails are held word for word by `src/notices/send/__snapshots__/english-mails.json`.
- The tools of a Spanish paragraph (B5): "Más" adds "Ver en inglés" last. It puts the English text in `.orig` inside the paragraph, after `.text`, from `/api/english/<ref>`; a press inside `.orig` does not mark the paragraph, and copy, image, and share read `.text` only. Parallels, terms, and the assistant take `lang`. The Bible and the other works stay in English with the tag "en inglés", and Spanish has no pair page and no study page. A share link made on a Spanish page is `/es/s/...`.
- This repo is public. No secret or DSN in the code.
- Text from the Papers always comes from the API. Never type a quotation. The one place where the repo holds text is `src/content/passages.ts`: a home passage is one or more whole sentences of a paragraph, copied from the API response, and the build fails if it differs from the API by one character (`excerptPassage`).
- The Hub's own copy makes no belief statement and no claim about the text.
- The site is `www.urantiahub.com` since the cutover of 2026-10-10. `SITE_ORIGIN` is that address and `SITE_INDEXABLE` is on. `next.urantiahub.com` redirects to www. A preview or a local run has neither setting, so it is never indexable.
- Paragraph references use the `--ref` token (darker than `--muted`), which meets WCAG AA. Kelson's rule: the design wins over a contrast score, so a change to `--ref` is a design decision, not a compliance one.
- `CHROME_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" bun run lighthouse` on this Mac. Lighthouse does not find Chrome without it.
- PostHog loads after the page load, when the browser is idle (`src/lib/when-idle.ts`). A static import of it in client code puts it back on the path to the first paint and fails the Lighthouse gate.
- No error-report vendor. Kelson removed Sentry on 2026-10-07: static pages, no accounts, Vercel keeps the server logs. If browser errors must be seen later, use PostHog error capture, not a second vendor.
- The Lighthouse performance gate is 0.85 since 2026-10-09 (Kelson). The paper page scores 0.87 to 0.93 on the test machine of GitHub, so a gate of 0.90 failed about one run in two on noise, with no change in the page. The gate still catches a real drop. Planned: one pass for speed at the end of the rebuild, and then the gate goes up again. Before that it was 0.90, not 0.95. The text face keeps its optical-size axis (a 109 KiB file, about 57 KiB more than without it) because the headings look finer with it, and Kelson chose the design. Without the axis the paper page scores 0.96. Do not drop the axis to raise the score.
- The theme is light by default and dark only by the reader's choice (`src/lib/theme.ts`, `data-theme` on `<html>`). The system setting does not decide. Do not add a `prefers-color-scheme` rule.
- Do not name a CSS class after a Tailwind utility. A class named `contents` removed a whole column (`display: contents`). The browser tests check the column layout.
- Both Literata font calls in `src/components/RootShell.tsx` give the family name "Literata", so the true italic is picked by the browser. Only the upright face is preloaded.
- The mark is a bookmark (`src/brand/BookmarkMark.tsx`). The icon files in `src/app/` and `public/` are written by `bun run icons` from that one shape. Do not edit them by hand. No concentric circles, and no mark shared with urantia.dev.
- Three colors, three meanings. Yellow (`--mark`) is the paragraph in focus. Green (`--voice-line`) is progress only: the line of the player, and the read marks. Indigo (`--accent`) is links and the reading position.
- The voice shows by the strength of the text, never by a color or a moving mark (Kelson, 2026-10-13; mock `mocks/hub-v2/voice-place.html` in the workspace). While it sounds: an ink bar beside the paragraph, the rest of the page at 34 percent while the page follows (`data-follow`, `data-fade` on `<html>`), and in the paragraph the sentence at full ink with the rest softer (`data-soft`, `::highlight(voice-now)` in `src/reader/voice-mark.ts`). A title that sounds is at full ink with no bar. A scroll by hand, or a marked paragraph, ends the fade; after the mark goes, the page returns at the next sentence. A pause keeps the bar (`data-held`). The page moves in 1.1 seconds, eased (`bring`), and jumps after the page was hidden.
- The voice plays ONE file for each paper when the API gives its time map (`paper.audio`, read by `paperAudio`): `src/audio/paper-engine.ts`. On a phone with the screen off, Chrome refuses or stalls a change of file, and one file has none. A paper with no map, or a map that does not cover each paragraph, keeps the old engine of one file for each paragraph (`engine.ts`).
- "Continue listening at {ref}" uses `hub:voice-place` in the browser (`src/reader/voice-place.ts`), named on the Privacy page.
- A paragraph is server HTML. No component exists for each paragraph. `ReadingNav` marks paragraphs with the attributes `data-picked` and `data-voice` through one click listener, and sets `data-reader` on `<html>` when it owns the marks. Before that, and with no JavaScript, CSS `:target` marks the paragraph.
- One voice: `nova`. The content gateway reads its URL from the API (`novaAudio`). No code builds an audio URL. A paper with one paragraph that has no audio gets no round button.
- Icons are family B (`src/components/icons.tsx`): tool icons are a line of 1.9 with round ends and a label below; player icons are solid. Check each new icon on one sheet with the full set, because two icons can look alike. The reader sees "Save" and "Saved", never "bookmark" (Kelson, 2026-10-09); the code and the API say `bookmark`. `saved` is the second solid icon: a paragraph that the reader saved. There is no "Highlight".
- Browser tests serve a silent MP3 file in place of each CDN audio file (`e2e/audio.ts`). No test loads audio from the CDN.
- A change of the pill's job must call `setHidden(false)`. The page scrolls down to follow the voice, so without it a pause hides the controls.
- The navigator lists the sections of this paper only. "All papers" goes to the contents page, which shows a "Continue" card from `src/reader/last-read.ts` (this browser; for a signed-in reader also the account). The theme control is an icon in the header, or in the reader settings on the pages that have them. The footer has none (Kelson, 2026-10-09).
- Search (`/search`): the server runs both searches through the content gateway and keeps each result (`searchExact`, `searchRelated`). The browser never calls the API, so the security policy has no API host.
- The search screen has no site header, so it ends with "Browse all papers", a link to the contents page, with and without a search (Kelson, 2026-10-09).
- A search snippet is a list of text parts from `src/search/snippet.ts`. React renders the marks. No snippet reaches the page as an HTML string.
- The first group is "Matches" (Kelson, 2026-10-18; mock `mocks/hub-v2/search-matches.html` in the workspace). The Hub sends no `type`, so the API's default mode decides: a reference, the exact phrase, all words, then close matches. A row whose `match` is `near` or `most` shows a small "close match" mark, and `meta.didYouMean` shows as "Did you mean …?" with a link that searches those words. A cut row has "Read more", a button outside the link that shows the whole paragraph in place (`wholeParagraph`); the text stays the link to the paragraph.
- `/search` stays out of each search engine: a `noindex` meta at each index setting, and a `Disallow` in `robots.txt`.
- Analytics never sends the typed text of a search. Events carry labels and count ranges, and `scrubSearchText` cuts the text from each address that PostHog records.
- The starter questions in `src/search/starters.ts` are approved copy. Before a question enters the pool, run it against the live search and read its first results. The reader sees one from each group, chosen before the first paint.
- Request-time content arrives as a stream, and a stream needs JavaScript to show. So search results need JavaScript. With none, `/search` gives a plain form, and the proxy sends a reference to its paper.
- The fixture server answers a search from `e2e/fixtures/search_*.json` and `semantic_*.json`. Other text gets an empty result, and the text "fail related" makes the semantic search fail.
- The server records each search with `logSearch` (`src/server/search-log.ts`): the text, the kind, and the counts, under one fixed name, with no link to a reader. The browser never sends the text. The Privacy page states both facts: change it when either one changes. The log skips a reader whose browser sends `Sec-GPC: 1` or `DNT: 1`. The browser analytics do not start for that reader (`initAnalytics`). The two must stay in step, because the Privacy page promises both. Its time is the date only, but PostHog also keeps the time of receipt, so the Privacy page makes no promise about time.
- After an API release that changes search, refresh the kept results: the revalidate route takes the tag `search`.
- The two search functions use `'use cache: remote'`, because the API has one rate limit for the whole site and each new text costs it two requests. The Vercel firewall has a rate rule for `/search` (and for the terms, the reader data, and the parallels).
- Next.js keeps the last pages alive but hidden, with an inline `display: none`. A CSS rule of the form `body:has(.some-page)` then stays true on each later page. Write `:has(.some-page:not([style*="display: none"]))`, and hold it with a browser test that moves between pages by links.
- A link to `/search?q=...` has `prefetch={false}`. A prefetch would run the search, and the firewall counts each request with `q` against the limit of 20 searches a minute for each IP address (rule "Rate limit search" in the Vercel firewall).
- A press that starts a search must show the grey rows at once (`useTransition` in `SearchBox`, and the `key` on the results wrapper in the page).
- On a paper page the site header is sticky. It leaves on a scroll down and returns on a small scroll up, with the bottom controls: `ReadingNav` sets `data-bars` and `data-scrolled` on `<html>`, and CSS does the rest. It never shows the paper title (Kelson, 2026-10-09).
- The icon of `ReaderSettings` is a person, and the reader's initial after a sign-in (Kelson, 2026-10-09). Its name is "Account and settings". While the site has no sign-in (`NEXT_PUBLIC_SIGN_IN` off) it is the sliders.
- The reader settings (`ReaderSettings`) hold the theme, the text size, and the account rows, and later translation and parallels. They are in the header of each page.
- The text size is a step from 0 to 4 (`src/lib/text-size.ts`). It sets `--reader-scale`, which sizes `.paper` only. A start script applies it before the first paint, as for the theme.
- An element with `backdrop-filter` or `transform` becomes the frame for its `position: fixed` children. The header has a blur, so a sheet that opens from it must be a child of the page body (`createPortal`).
- The Privacy page is built from lists in `src/content/privacy.ts`: the companies that handle data (`VENDORS`), the things kept in the browser (`BROWSER_ITEMS`), the date, the contact address, and the company that runs the site (Adams Technologies LLC). A new vendor or a new stored item is one entry there, with a new date. Each statement on the page must be true of the live code, and the page makes no promise about the future. No lawyer reads it (Kelson, 2026-10-09): write it with care and plain facts. The facts of accounts (`ACCOUNT_ITEMS`, `ACCOUNT_VENDORS`, the cookies) show only while `NEXT_PUBLIC_SIGN_IN` is `on`, so the page is true in both cases. A new thing that an account holds is one entry in `ACCOUNT_ITEMS`.
- The text of a paper has no glossary mark, and the HTML of a paper holds no term data (Kelson, 2026-10-08: marks looked random). A reader taps a paragraph and presses "Terms". The browser then asks `/api/terms/<ref>`, which answers the names and the ideas with each description, so an entry opens with no second request.
- The glossary is a committed file, `src/content/glossary.json`, written by `bun run sync:glossary`. Do not edit it by hand. The nightly contract test fails when the live count differs: then run the sync and commit.
- The Hub finds the terms of a paragraph itself (`src/glossary/match.ts`). It does not use the paragraph links of the API, which are a topic index and not word positions. Rules: whole words; the longest name wins; a name with capitals needs the same capitals; a plain plural matches; another name counts only for a name, never for an idea, and only if it reads as a name (a capital or more than one word, and no small word such as "the" or "his" at its start); a name that two entries claim goes to the one that the Papers cite at least three times more, or to neither; an order or a race also claims its name in the singular; a short list of ideas that are a verb or a small word in most sentences never matches (`PLAIN_WORDS`); an idea that the glossary marks `sense: "ordinary"` (a word in its everyday sense, such as "man" or "gold") never matches; an entry that is only a number never matches. Before a change to these rules, run the matcher on the recorded paragraphs and read the result: a wrong term is worse than no term.
- The glossary is 1.7 MB. Only server code imports `@/glossary/glossary` or `@/glossary/match`. A client component imports the types of `@/server/terms` only.
- The row of a marked paragraph is Save, Note, Share, More. "Terms in this paragraph" and "Copy the text" are in "More". Save and Note are absent while the site has no sign-in.
- The terms address reads the text of one paragraph with `getParagraphText`, which uses the shared remote cache. The cache holds one item for each paper. The check for a missing paragraph is outside the cached call, because an error loses its kind when it crosses a cache (a 404 became a 502). The firewall has a rate rule for `/api/terms/`.
- Sign-in (step 5b) is in `src/account`. A reader signs in with a UrantiaHub account through `@urantia/auth/server`; the app is `urantiahub-app`, which is first-party, so there is no permission screen. Two settings turn it on: `HUB_APP_SECRET` (server; the app secret, and the source of the cookie key) and `NEXT_PUBLIC_SIGN_IN=on` (what the pages show, and the routes too: `deps.ts` reads both). With either one missing, nothing of the sign-in shows and each route answers "signed out".
- On https the cookies that only the server reads have the `__Host-` prefix (`cookieNames` in `handlers.ts`): a browser takes such a cookie only from this host, so a page on another host of the site cannot plant a session or a sign-in start. They need the path `/` and no domain. A local run on http uses the plain names.
- Only a 401 or a 400 at the token refresh ends a sign-in (`isRefusal` in `call.ts`): the API answers 401 for a session that is over, and 400 for a refresh token that it cannot read. The package calls each 4xx "refused", but a limit (429) or a block (403) says nothing about the session.
- A call to the API for a reader has a limit of 8 seconds (`inTime`), so the answer with a new session cookie always returns.
- A page that the browser shows again from its memory (Back) loads again when its reader is not the reader of the browser now (`onPageShown`).
- The Privacy page must name each thing that `src/account` writes to the account or keeps in the browser. A new one is a new line there, in the same change.
- The tokens live in one encrypted cookie that a script cannot read (`hub_session`). The browser never holds a token. `hub_in` holds only "1", so a page knows before it asks that a reader is signed in: a signed-out reader costs no request. The cookie names are in `src/account/cookies.ts`, which browser code can import; `session.ts` holds the encryption and must stay out of the browser bundle.
- No page reads a cookie on the server. Each page stays static. The browser asks `/api/auth/session` one time for each page load, and only when `hub_in` is there.
- Each account route is one line in `src/app` and its logic is in `src/account/handlers.ts`, with the real dependencies in `deps.ts`. A new route for a reader's data goes through `handleReader`: it checks where the request comes from (a read too), refreshes the token, saves a new session, and signs the reader out only when the API refuses. An outage never signs a reader out.
- The Hub does not pass `/me` of the API through. Each `/api/me` route does one job and checks its input (`src/account/data.ts`).
- The place and the language of a signed-in reader live in the reader's preferences in the API, under `hub.place` and `hub.lang` (`{ lang, at }`). The theme and the text size stay on each device and never go to the account. That record is one for all apps, so each Hub key starts with `hub.`. Each value holds the time of its last change (`at`), and the newer one wins (`newer` in `reader-data.ts`).
- When a signed-in reader is signed out, by a press, by the server, or because the session ended, the place leaves this browser (`forgetAccountData`). A second person can sign in on the same browser, and the first person's place must not show to them or go into their account. The theme and the text size stay.
- A page says which reader it speaks for: each `/api/me` request carries `x-hub-reader`, a key that the session answer gives (`readerKey`; not the id, not a secret). The server answers 409 when the session is another reader's, and the page then drops what it holds and asks again who is signed in. This covers a tab that stayed open from before a sign-out. The browser mark `hub:account-data` holds the same key, and an answer that arrives after a sign-out is dropped (`epoch` in `sync.ts`).
- What a page collected (a waiting place, waiting read marks, the list of read papers) belongs to one reader (`collectedFor` in `sync.ts`). Each path that adds or sends calls `ready()` first, which drops it all when the reader of the page changed. Do not read a waiting value before that call.
- A sign-out counts only when the server answered. If it did not, the page says that the reader is still signed in.
- A sign-out does not end the session of the accounts site (Kelson, 2026-10-08). So the next sign-in asks for the sign-in page (`hub_ask_account`).
- The account rows are at the end of the reader settings: "Sign in", or ONE row with the reader's name that opens accounts.urantiahub.com, and "Sign out" (Kelson, 2026-10-09). The contents page shows one invitation to a signed-out reader. Its words name saved paragraphs and notes first.
- Browser tests use a stand-in for the accounts site and for the reader's data (`e2e/account-standin.ts`, on the fixture server). Each test is one reader of its own (`asReader`), so the tests run at the same time.
- One header on every page (Kelson, 2026-10-24; spec `docs/superpowers/specs/2026-10-24-urantiahub-v2-site-header-design.md` and mock `mocks/2026-10-24-hub-nav/` in the workspace): on the left the mark, then the way back where a parent page exists (`HeaderBack`, `PairBack`); on the right search, contents, the EN/ES pill, and the account, in that order, each in a box of a fixed width (`data-slot`), so no control moves from page to page. No page hides one; the pill is absent only while `NEXT_PUBLIC_SPANISH` is off. The name "UrantiaHub" shows on the home page only, and stays in the HTML for a screen reader on each other page. No page links in the header: "About" is in the footer. On the contents page the list icon is the current page (`aria-current`). `e2e/header.spec.ts` measures the places on each page. The settings of a page with no text of a paper have no text size. The search screen has no site header.
- A paragraph counts as read after a time in the reading zone of the screen that fits its length: 12 ms for each character, between 1 and 8 seconds (`src/reader/read-tracker.ts`). A fast scroll marks nothing, and a hidden page counts no time. With the voice the page follows the sound, so the same rule covers it. Only a signed-in reader has a record (`ReadMarks`); a reader with no account sends nothing.
- Read paragraphs go to the account as one batch, at most one time in 30 seconds, and when the reader leaves the paper or hides the page (`queueRead`, `flushRead` in `sync.ts`). A batch that failed waits for the next try. A sign-out empties the queue.
- A paper counts as "Read" at nine of ten paragraphs (`READ_SHARE` in `data.ts`). The contents page shows "Read", or "Section 3 of 7" for the paper of the reader's place, to a signed-in reader only (`PaperMark`). The count of sections of each paper is in `paper-index.json`, written by `bun run sync:index`.
- The word beside a paper uses `--voice-line`. Green means progress here (Kelson: progress is green and only grows).
- A browser test that needs time to pass moves the clock of the page (`page.clock`). It does not wait.
- Not built from the step 5b spec: the `section_read` event. Kelson decides after a look at the PostHog event count; the plan must not need an upgrade.
- Step 6 (saved paragraphs and notes) is live. A reader with no account cannot save: Save and Note ask for a sign-in in one short line, and the sign-in returns to the paragraph with the row open. Nothing of a saved paragraph or a note goes into the browser's storage (`src/account/saved.ts` holds it for the life of the page, for one reader).
- All notes are private. A note is plain text of 5,000 characters at most (`NOTE_MAX` in `src/account/note-limit.ts`; the server checks it too). The field takes more than that, so a paste loses nothing: near the limit a count shows, past it the count is below zero in `--danger` and "Save" is off (Kelson, 2026-10-09). `--danger` has no other use. Notes read as a thread: the oldest first, and the field for a new note at the end.
- The reader routes are `/api/me/saved`, `/api/me/bookmarks`, and `/api/me/notes[/id]`, all through `handleReader`, with their checks in `src/account/saved-data.ts`. A refused value answers `{ ok: false, why }` with status 200, as the other reader routes do. The API keeps one list for a reader, so the Hub shows what each app saved for that reader.
- Save shows at once and goes to the account behind it; two fast presses go in their order (`toggleBookmark`). A note shows when the account took it, and until then the text stays in its field.
- Each paragraph has an empty `.marks` place beside its reference, in a line of a fixed height (`.refline`). `SavedMarks` puts the marks there with a portal, so a mark moves no text. A browser test compares positions before and after the marks arrive, and it fails when a mark has a height. The text of a paragraph is `.text`.
- A press on a paragraph belongs to `ReadingNav`. The pen (`.mark-notes`) and a note in a margin card (`data-notes-for`) have no handler of their own: the one click listener opens the notes.
- From 1100 px the notes sit in cards in the right margin (`MarginNotes`, placed by `placeCards`), and the pen hides. Below that the pen shows with the number of notes. A card shows the newest note; up to three open in place; a longer thread links to `/saved?ref=`.
- `Sheet` (`.panel`) is the small panel above the controls: More, the sign-in question, and the notes. The class `sheet` belongs to the navigator.
- `/saved` lists what the reader saved (search, filters, sort in the browser, `src/saved/list.ts`). With `?ref=` it is the page of one paragraph: the whole paragraph, all its notes, and the field. It has `noindex`, it is not in the sitemap, and `robots.txt` disallows it. The list has no field for a new note.
- The contents page keeps the room of its cards from the first paint: a script before them marks `<html>` with `data-place` or `data-guest`, and CSS shows the invitation by those marks. It has no link to Saved (Kelson, 2026-10-19: the pill was noise); the settings hold it. A card that appears after the load moves the list (Kelson, 2026-10-09). A new card there needs the same.
- The code for notes loads at the first use (`lazy` in `ReadingNav` and `SavedMarks`). A reader with no account does not download it.
- Events for saved things carry the paper only: `bookmark_added`, `bookmark_removed`, `note_saved`, `note_deleted`. Never a reference, never text.
